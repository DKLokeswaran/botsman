# Known issues

Accepted low-severity issues. Each row is a real issue that has not been fixed yet.

| Issue | Where | Why it is low |
| --- | --- | --- |
| Tokens with extra dot-separated segments are accepted; the extra part is ignored, and the valid parts are still required | `server/src/auth/auth-service.ts` | Grants nothing an attacker didn't already have |
| A pending approval whose waiter never starts (a crash between creating it and saving its memo, or a restart with sandboxes broken) never expires and stays in Needs you | `server/src/permissions/permission-policy.ts` | Rare; answering it does nothing harmful |
| A folder name starting with `..`, such as `~/.botsman/..x`, counts as outside its parent, so such a folder is accepted inside Botsman's data and `read ..notes.md` asks for approval | `server/src/bots/folder-policy.ts`, `server/src/backup/backup.ts` | The accepted folder is a new, empty one |
| A bot name of only spaces is accepted, `PATCH` doesn't trim names, and a default model with an unknown provider is accepted | `server/src/bots/bot-service.ts`, `server/src/bots/bot-registry.ts` | Owner input only; the bot answers with `model_not_connected` |
| An approved memory edit overwrites an owner edit made to the same file while the approval waited | `server/src/memory/memory-edits.ts` | Needs the owner to edit and then approve the same file |
| A chat left open while its app is in the background still marks new replies read, and the preview shows Markdown symbols as typed | `packages/client-core/src/chat-controller.ts`, `server/src/bots/bot-activity.ts` | The reply is still in the chat; alerts come from the alerts stream, not the unread count |
| Compacting a chat too short to summarize runs the save turn and then shows nothing more | `server/src/engine/compaction-guard.ts` | The save turn's notes are kept; the chat is simply not shortened |
| Usage history leaves out the model calls that write compaction summaries, which Pi makes without a reply in chat | `server/src/usage/usage-log.ts` | One summary per compaction; replies, which cost the most, are all counted |
| A pending send is matched to the server's copy by its text, so the pending copy can stay a moment longer when the server changes the text | `packages/client-core/src/chat-state.ts` | The server stores the text as sent; a failed send is never dropped this way |
| Neither WebSocket has a deadline for the first `hello`, so an unauthenticated connection can stay open | `server/src/api/socket.ts`, `server/src/api/alerts-socket.ts` | One idle socket each; messages are capped at 64 KiB |
| The restore steps say devices must sign in again without `secret.key`, but refresh tokens don't need it; the overview places the pre-compaction save in `memory`, but it lives in `engine/compaction-guard.ts` | `docs/operations/server.md`, `docs/decisions/overview.md` | Docs only |
| Two setup requests racing on first run make the loser fail with 500 instead of 409 | `server/src/api/auth-routes.ts` | First run only; the winner is set up correctly |
| Finished provider sign-ins stay in memory until restart | `server/src/providers/provider-logins.ts` | Small, owner-started objects |
| Only the guard's pure logic is tested for a restart between the save turn and its compaction; `BotSession`'s check on open has no integration test | `server/src/engine/bot-session.ts` | The guard's decisions are covered; only the wiring isn't |
| No test covers a rate-limit window expiring, or a sign-in error other than a wrong password giving its count back | `server/src/auth/rate-limit.ts`, `server/src/api/auth-routes.ts` | Parallel and correct-password cases are covered |
| `forgive` can take back a count from a newer window when the 15-minute window rolls over during a password check | `server/src/auth/rate-limit.ts` | At most one extra guess per concurrent correct sign-in, which needs the password |
| After setup, each `POST /api/setup` answered 409 still uses the setup limit, and the 11th gets 429 with the sign-in message | `server/src/api/auth-routes.ts` | Setup is first-run only; the server's state isn't exposed beyond what `GET /api/setup` says |
| Save turn entries written before request ids were stored on them aren't settled after a restart, so one extra save turn can run | `server/src/engine/compaction-guard.ts` | Only session files from development builds have such entries |
| When the guard waits on a leftover save turn after a restart, it acts on the view read before the wait, so a compaction Pi ran meanwhile can be followed by a second one | `server/src/engine/compaction-guard.ts` | Needs a restart mid-save and Pi's own compaction during it; costs one extra summary |
| A finished save turn whose compaction keeps failing, or was stopped, is compacted again after every reply until one succeeds | `server/src/engine/compaction-guard.ts` | One summary request per reply; Pi's own compaction at its threshold behaves the same |
| A queued message that follows a run ended during its tool round (stopped, a model error, interrupted, or the restart limit) looks steered, so after such a save turn the next reply near the limit asks no new save | `server/src/engine/compaction-guard.ts` | Needs a save turn that ended during its tool round; Pi's own compaction still runs at its threshold |
| The guard relies on Pi's default steering mode, one message per tool round, which the server leaves unset and no doc records; setting `steeringMode: "all"` would make back-to-back steers look like new turns | `server/src/engine/compaction-guard.ts`, `server/src/engine/bot-session.ts`, `docs/decisions/conversations.md` | Holds with the current settings; only a future settings change breaks it |
| The comment on `steered` doesn't say the walk back skips tool results and other entries between the message and the reply | `server/src/engine/compaction-guard.ts` | Comment only |
| pnpm installed under `~/.local/bin` is not on the `PATH` until the next login, and stays off it when a `~/.bash_profile` or `~/.bash_login` stops bash reading `~/.profile`; the script doesn't say where it put pnpm | `deploy/install.sh`, `docs/operations/server.md` | The install itself uses the full path; only later hand-run `pnpm` commands are affected, and `~/.local/bin/pnpm` works |
| `apt-get update` failing on an unrelated repository, such as one with an expired key, stops the bubblewrap install | `deploy/install.sh` | The apt error names the broken repository; installing bubblewrap by hand and running the script again works |
| A failed `sudo` in the AppArmor step, such as an owner without sudo rights, stops the install there instead of warning and carrying on | `deploy/install.sh` | It stops before dependencies or the service are installed, the `sudo` error is on screen, and the docs say the step needs `sudo` |
| With `USER` unset, `set -u` stops the script at the linger line before its fallback runs | `deploy/install.sh` | SSH logins and systemd always set `USER`; the service is already running |
| The AppArmor comment says the profile was not the cause when `bwrap` still fails after loading it, but a `bwrap` outside `/usr/bin`, which the profile doesn't cover, fails for that reason too | `deploy/install.sh` | Comment only; the warning still points to `/api/health` |
| The bwrap warning and the linger hint go to stdout, while `fail()` uses stderr, so a log split by stream shows a clean install | `deploy/install.sh` | Both lines print just before the closing banner in a normal run |
