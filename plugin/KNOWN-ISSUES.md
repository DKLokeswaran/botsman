# Known issues

Low-severity issues in the `hermes-bots` plugin, its contract and its tests. None of them affects normal routine delivery or alerts.

## Delivery and routine output

| Issue | Where | Effect | Suggested fix |
| --- | --- | --- | --- |
| A routine name containing a newline breaks the routine message format | `plugin/hermes-bots/routine_output.py` (`parse_target`, `routine_message`) | A name such as `Morning%0Abriefing` produces `[Routine: Morning\nbriefing]`, which does not match `RoutineMessage` in the contract, so the apps show it as a plain bot message | Replace control characters in the decoded name with spaces |
| The cron footer stays in the output when the output ends with whitespace after it | `plugin/hermes-bots/routine_output.py` (`_WRAPPED`) | "To stop or manage this job…" lands in the chat. Hermes's cron output has not ended with whitespace so far | Allow trailing whitespace before `\Z`, or strip the content first |
| The footer match depends on its exact English wording | `plugin/hermes-bots/routine_output.py` (`_WRAPPED`) | If Hermes rewords the footer, it lands in the chat | Match the header and separator strictly and the footer loosely, and log when it does not match |
| `parse_target` accepts a target without a routine name | `plugin/hermes-bots/routine_output.py` | `session-<id>` is delivered as "Routine", although the contract's `DeliverTarget` requires `/<name>` | Refuse a target without the `/<name>` part |
| `format_target` does not check the session id | `plugin/hermes-bots/routine_output.py` | A session id containing `/` or `,` would produce a target that is parsed wrongly. Hermes session ids contain only digits, `_` and hex | Raise when the session id contains `/` or `,` |
| One failing row delays the later rows of the same chat | `plugin/hermes-bots/store.py` (`_CLAIMABLE_SQL`) | A row in error backoff holds back the chat's later routines for up to about a minute. This keeps routines in order | State the ordering choice in a comment above the query |
| Delivered routine text stays in the store for 7 days | `plugin/hermes-bots/store.py` (`finish_delivery`, `prune`) | The shared store holds a second copy of routine output until pruning | Clear `text` when a row is finished |
| `send` and `_standalone_send` repeat the same queue-and-log code | `plugin/hermes-bots/__init__.py` | Two copies to keep in step | Move the shared part into one helper |
| A routine for a deleted profile creates an empty session database | `plugin/hermes-bots/delivery.py` (`write_under_lease`) | Hermes's `acquire` creates the missing folder and `state.db` before the row is dropped as "chat not found" | Drop the row when its `db_path` does not exist, before acquiring |
| The retry lookup builds its file URI without escaping and does not retry a brief WAL recovery error | `plugin/hermes-bots/delivery.py` (`_find_message`) | A Hermes home path containing `#`, `?` or `%` opens the wrong file, possibly creating an empty one; a WAL recovery window makes the read-only open fail | Build the URI with `Path(db_path).as_uri()` and retry a "disk I/O error" briefly, as Hermes's own read-only opens do |
| A failed retry lookup counts as a failed delivery attempt | `plugin/hermes-bots/delivery.py` (`_find_message`, `_retry_or_drop`) | Five lookup failures drop the row with `routine_failed`, even when its message already landed | Defer without counting an attempt when the lookup itself fails |
| The retry lookup reads the whole messages table | `plugin/hermes-bots/delivery.py` (`_find_message`) | Hermes indexes `message_uid` only together with `session_id`, so the lookup scans the table. It runs only on a retry after an interrupted write | Also filter by the chat's sessions, or accept the cost and say so in a comment |
| A worker stall of more than 60 s restarts a row's busy stretch | `plugin/hermes-bots/delivery.py` (`_busy_stretch_start`) | Repeated stalls in the single worker thread delay the 15-minute drop | Record busy checks with their own timestamps instead of reading `next_attempt_at` |
| Every process that loads the plugin starts a worker thread | `plugin/hermes-bots/__init__.py` (`register`) | Short-lived processes, such as cron runs, poll the store for as long as they live. Whether a gateway serving several profiles runs one worker per profile copy is unverified | Start the worker once per store path, or only in long-lived processes plus the process that queues a row |
| A reused PID keeps a dead worker's claim until the claim timeout | `plugin/hermes-bots/store.py` (`_holder_is_dead`) | Hermes's probe reads a recycled PID as alive, so the row waits up to 5 minutes | Accept: the probe is conservative by design |
| The delivery module docstring and the drop reason are out of date | `plugin/hermes-bots/delivery.py` | The docstring says the worker runs in "each long-lived process"; it runs in every process that loads the plugin. The drop reason spells out "15 minutes" instead of deriving it from `BUSY_LIMIT_S` | Update the docstring and format the reason from the constant |
| A routine whose output cannot be queued raises no alert | `plugin/hermes-bots/__init__.py` (`send`, `_standalone_send`) | When queuing fails, for example on a read-only store or a target that no longer parses, Hermes records a delivery failure in the run history but the apps get no `routine_failed` alert | Raise `routine_failed` for the target's chat on a best-effort basis, logging when that fails too |
| The worker id is fixed when the module is imported | `plugin/hermes-bots/delivery.py` (`WORKER_ID`) | Unverified. A process forked after the plugin loads would share its parent's worker id, so either could release or finish the other's claim. No Hermes process is known to fork after loading plugins | Regenerate the id when `os.getpid()` differs from the PID in it |
| The adapter's `connect()` does only the minimum | `plugin/hermes-bots/__init__.py` (`HbappAdapter.connect`) | Unverified. It marks the adapter connected and returns; whether `BasePlatformAdapter` expects more from `connect()` has not been traced. Scheduled delivery works in the integration tests | Trace `BasePlatformAdapter`'s connect contract before a Hermes upgrade |
| A worker id can lack the PID namespace stamp without a warning | `plugin/hermes-bots/delivery.py` (`_new_worker_id`) | Unverified. On Linux, Hermes's stamp is empty when it cannot read `/proc/self/ns/pid`, without raising; the id is fixed for the process's life, so its claims always wait the claim timeout and nothing is logged | Warn when the stamp is empty on Linux too |
| An unexpected error from Hermes's stamp function stops the plugin from loading | `plugin/hermes-bots/delivery.py` (`_new_worker_id`) | Suspicion. Only `ImportError` falls back; any other exception at import time takes down the platform and the hooks. Hermes's current function handles its own errors | Fall back to an empty stamp on any exception |
| The missing-stamp warning overstates the effect off Linux | `plugin/hermes-bots/delivery.py` (`_new_worker_id`) | It says claims wait for the claim timeout; on Windows and macOS Hermes still probes unstamped holders | Say the wait applies on Linux |
| Claims left by workers from before the stamp wait the claim timeout once | `plugin/hermes-bots/store.py` (`_holder_is_dead`) | On Linux, Hermes never probes an unstamped holder, so rows claimed by a crashed worker of an older plugin version wait 5 minutes after the upgrade | Accept: it happens once per upgrade |
| `_hermes_holder_probe` has no return annotation | `plugin/hermes-bots/store.py` | The rest of the module is fully typed | Annotate it as `Optional[Callable[[str], bool]]` |
| A long lock on the session database may count as a failed attempt | `plugin/hermes-bots/delivery.py` (`process_next`) | Unverified. If taking the turn lease raises "database is locked", five such attempts drop the row with `routine_failed`; Hermes itself treats a locked lease as busy | Treat a "locked" error like a busy chat and defer without counting an attempt |

## Alerts and the alert stream

| Issue | Where | Effect | Suggested fix |
| --- | --- | --- | --- |
| The turn-start map is trimmed only by age | `plugin/hermes-bots/alerts.py` (`_remember_turn_start`) | More than 2,000 turns started within 24 hours are all kept until they are 24 hours old. The memory used is small | Also drop the oldest entries when the map is over its cap |
| A malformed `since` uses up the one-time ticket | `plugin/hermes-bots/dashboard/plugin_api.py` (`alerts`) | The client gets the same HTTP 403 as for a bad ticket and cannot tell the two apart | Check `since` before the login check, still before accepting, and document the refusal |
| The subprotocol echo relies on a private Hermes attribute | `plugin/hermes-bots/dashboard/plugin_api.py` (`_hermes_ws_subprotocol`) | If Hermes renames it, clients that send the ticket as a subprotocol cannot connect | The integration tests cover it; run them before every Hermes upgrade |
| Routine runs are not filtered out of approval and question alerts | `plugin/hermes-bots/alerts.py` (`_is_routine_run`) | The human-input hooks carry no `task_id`, so the check never applies to them. Routine runs cannot ask a person today: Hermes settles their approvals itself and turns off clarifying questions | Detect a routine run from Hermes's cron session context, and use the real hook payload in the unit test |
| A negative `since` replays from the start | `plugin/hermes-bots/dashboard/plugin_api.py` (`_start_id`) | `since=-3` is treated as `since=0` and replays up to 500 alerts instead of being refused | Refuse negative values before accepting |
| A `since` above the largest SQLite integer ends the stream after it opens | `plugin/hermes-bots/dashboard/plugin_api.py` (`_start_id`) | The first store read raises `OverflowError`, which the route does not catch | Refuse values above 2^63 - 1 before accepting |
| A store error ends the alert stream | `plugin/hermes-bots/dashboard/plugin_api.py` (`_stream`) | Any error other than a disconnect, such as a long lock, closes the stream; the app notices only through the missing pings | Log the error and retry the read on the next poll |
| `HERMES_BOTS_FINISHED_AFTER_S` accepts `nan` and negative values | `plugin/hermes-bots/alerts.py` (`_finished_after_s`) | `nan` silently stops `finished` alerts; a negative value raises one for every completed reply | Fall back to the default unless the value is finite and positive |
| Hook alerts may name a different chat id than routine alerts after a chat is compressed | `plugin/hermes-bots/alerts.py` | Unverified. Hook alerts use the session id Hermes passes, which may be a continuation id; the contract promises the stored id | Check on a test instance after a compression, then resolve to the stored id or reword the contract |

## Contract and docs

| Issue | Where | Effect | Suggested fix |
| --- | --- | --- | --- |
| The README's ping example leaves out `latest_alert_id` | `plugin/README.md` (Alert stream) | The code and the contract's `Ping` include it | Show the full ping message and say what the field holds: the last alert id sent on this stream |
| `ARCHITECTURE.md` does not say the routine name in the target is percent-encoded | `docs/research/ARCHITECTURE.md` (Routines) | The code, README and contract require it, because cron splits targets on commas | Say "percent-encoded routine name" there |
| The plugin needs `plugins.isolation: in_process` | `plugin/README.md` (Install), `docs/research/BLOCKERS.md` (B18) | Under `plugins.isolation: host`, Hermes mounts no plugin WebSocket routes and does not support `register_platform`, so the alert stream and the `hbapp` platform disappear while installs and `/info` still succeed. `in_process` is Hermes's default | State the requirement in the README's Install section and in B18 |
| The docs leave out the drop after repeated write errors | `plugin/README.md` (Routines), `docs/research/ARCHITECTURE.md` (Routines) | Both name only "busy for 15 minutes" and "chat not found"; a row is also dropped with `routine_failed` after 5 failed writes, about 30 s after the routine ran | Add "or writing fails 5 times in a row" to both |
| The docs name only Host and Origin for `_ws_request_is_allowed` | `docs/research/ARCHITECTURE.md`, `docs/research/BLOCKERS.md` (B17), `plugin/README.md` | The function also refuses peers by IP address, which the socket therefore enforces too | Name the peer check alongside Host and Origin |
| The PRD lists an "errors" alert that has no alert kind | `docs/product/PRD.md` (FR-PUSH-1) | The contract's `AlertKind` and ARCHITECTURE's push table have no error alert, so the PRD and the design disagree | Add an `error` kind raised for failed replies, or remove "errors" from FR-PUSH-1 |
| The `mockups/app.html` path reads as a URL in the mockups README | `mockups/README.md` | The README serves `mockups/` as the web root, where the page is `/app.html`; `mockups/app.html` is its path from the repo root | Say both: the file is `mockups/app.html`, served as `/app.html` |

## Tests

| Issue | Where | Effect | Suggested fix |
| --- | --- | --- | --- |
| The integration ping test passes on any message | `plugin/tests/integration/test_alert_socket.py` (`test_a_quiet_stream_pings`) | It does not prove a live dashboard sends pings. The unit test `test_a_quiet_stream_pings` in `plugin/tests/unit/test_plugin_api.py` does | Assert the message type is `ping` on a stream that starts after the newest alert |
| The fake session database models only part of Hermes's write guard | `plugin/tests/unit/test_delivery.py` (`FakeSessionDB`) | It rejects a write without the lease, but does not model the lease expiring or a process stopping between the write and `mark_write_started` | Let the fake expire the lease on demand, and add a test that stops between the two steps |
| Smaller gaps in the unit tests | `plugin/tests/unit/test_delivery.py`, `plugin/tests/unit/test_plugin_api.py` | No test of a slow writer racing a claim takeover, of the types of `ts`, `id` and `store_schema` in sent messages, or of a socket where Hermes sets no subprotocol attribute | Add those cases |
| Socket refusals are only partly covered against a real dashboard | `plugin/tests/integration/test_alert_socket.py` | The header test sends a fake grant, which Hermes's own plugin socket gate refuses before the plugin's check runs; nothing tests the chat-off refusal on a live dashboard | Test with a real Desktop grant, and add a chat-off case |
| Untested delivery and socket edge cases | `plugin/tests/unit/` | No test of the retry lookup on a WAL database or a path that needs escaping, of the busy stretch continuing when another worker takes a row over, of the safe default when Hermes's chat flag is missing, or of the `store_schema` value in `/info` | Add those cases |
| The recovery test checks the chat message but not the row or its alert | `plugin/tests/integration/test_recovery.py` | A regression where the message lands but the row stays pending with no `routine` alert would pass | Also wait for the row's `written` state and assert its `routine` alert |
| No test of the missing-stamp fallback or of finish-and-alert atomicity | `plugin/tests/unit/test_delivery.py`, `plugin/tests/unit/test_store.py` | Nothing checks the id and warning when `hermes_state_pidns` is missing, or that a failing alert insert leaves the row pending | Add both tests |
| Unused `monkeypatch` parameters | `plugin/tests/integration/test_alert_socket.py` (`test_a_quiet_stream_pings`), `plugin/tests/unit/test_alerts.py` (`test_the_first_start_of_a_turn_counts`) | Noise in the test signatures | Remove them |
